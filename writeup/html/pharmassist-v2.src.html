The design is one question in, one answer out: no clarifying turns. Each question is answered on its own; the UI groups a user's questions into conversations. Answers that fail the rule are stored in messages but never cached.

Hosting

Static IPs and sticky HTTPS in front, scale-to-zero indexing behind

  • ① The hostname's A records point at the two EIPs (one per AZ); the NLB preserves the client IP for the WAF and the limits.
  • ② HTTPS ends at the ALB with a free ACM certificate; 80 redirects to 443; target-group stickiness 1 day.
  • ③ Auto Scaling group min 2 / max 4 (CPU 60 %), rolling replacement on deploy; no NAT gateway (≈ $32/month saved).
  • ④ The database and the cache accept connections only from the app, worker and migration security groups.
  • ⑤ Docling needs 8–16 GB, so indexing runs on a Fargate task (4 vCPU, 16 GB) that a backlog alarm starts and stops.

Corpus

Children match, parents explain, rows and figures are cited by id

Why rows exist: in the first index, generic prior-authorization text outranked the one PDL row that answered a drug question. Two exact lookup tools (lookup_va_formulary, lookup_ny_medicaid_drug) return rows by drug and dosage form, with explicit outcomes such as no_matching_row, which the prompt says never means “not covered”. Figures: raster flowcharts that Docling's layout model misses are inventoried from the PDF, read once by a vision model, and checked by code (edges point at real boxes, box text found by OCR) before they are chunked.

Hybrid retrieval: two queries, two signals, fused twice

Agent

Six lookups, 25 seconds, then submit; a citation must point at evidence a tool returned

Ingestion

An upload is live in one transaction, and the worker costs nothing between uploads

Each answer is one LangSmith run with inputs, outputs and metadata (user, conversation, provider, model, fallback, cached, latency, cost, tokens, index generation).
